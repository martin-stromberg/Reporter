## Fehlende oder unvollständige Planbestandteile

- [ ] **Lücke 1 — `MarkAllReadConfirmationText` wird nach einzelnem Als-gelesen-Markieren veraltet (stale):** Der Plan aktualisiert den Dialogtext ausschließlich in `LoadPageAsync` bei `append == false` (Programmablauf Schritt 6). `MarkReadAsync` entfernt Artikel ohne Paket-Neubewertung — korrekt für `_currentPacket`, lässt aber den Anzeigetext unverändert. Erreichbarer Ablauf: Paket mit 7 Artikeln laden → 3 Artikel einzeln als gelesen markieren → Doppelhaken tippen → Dialog zeigt „7 ungelesene Artikel vom &lt;Tag&gt;", tatsächlich werden nur noch 4 ungelesene Paket-Artikel markiert. Das ist genau die irreführende Anzeige, die der Plan mit der neuen Eigenschaft ausdrücklich vermeiden will (Designentscheidung „Bestätigungsdialog": „ein irreführender Titel ist kein zulässiger Planansatz"). **Fehlend:** Eine Festlegung, wie der Text konsistent bleibt — z. B. Mitdekrementieren in `MarkReadAsync` (alle entfernten Artikel gehören definitionsgemäß zum Paket), Neuberechnung via `GetUnreadPacketCountAsync` beim Öffnen des Dialogs in `OnMarkAllReadTapped`, oder eine ausdrücklich dokumentierte Abweichung.
- [ ] **Lücke 2 — `CardPositionText` (Kartenlayout) ist von der Paket-Begrenzung betroffen, aber nicht entschieden:** `CardPositionText` (`UnreadViewModel.cs:285-287`) zeigt `"{pos} von {Math.Max(UnreadCount, _articles.Count)}"` — Nenner = **Gesamt**-Ungelesenzahl. Mit paket-begrenzter Liste zeigt der Kartenstapel z. B. „3 von 42", obwohl nur 7 Karten existieren und Position 42 nie erreichbar ist (`LoadMore` endet am Paketende). Scope-Ausschluss 6 legitimiert die globale Gesamtzahl nur für `UnreadBadgeText`, `UnreadCount` und Chip-`Count`s — `CardPositionText` ist weder dort genannt noch sonst im Plan behandelt. **Fehlend:** Eine dokumentierte Entscheidung — entweder `CardPositionText` ausdrücklich unter die Begründung von Ausschluss 6 aufnehmen (da die Ausschlüsse anwenderbestätigt sind, ggf. als Ergänzung dokumentieren/bestätigen lassen) oder einen paket-bezogenen Nenner festlegen.

## Hinweise

- **Wortlaut-Ungenauigkeit `packet == null`:** Programmablauf Schritt 4 sagt „`packet == null` → leere Liste", die Designentscheidung „Paging-Abfrage" definiert `packet == null` dagegen als „unbegrenzt". Ergebnis ist praktisch identisch (`_currentPacket == null` ⇔ keine ungelesenen Artikel → leere Treffermenge), sollte aber der Klarheit halber vereinheitlicht werden.
- **`MarkAllReadAsync` bei `_currentPacket == null`:** Der Guard ist genannt, nicht aber das Verhalten im Null-Fall (vermutlich Markierung überspringen und trotzdem `LoadAsync`). In der Praxis durch den `HasArticles`-Guard des Buttons abgedeckt — als Implementierungsvorgabe präzisieren.
- **E2E-Fixture-Zeitzonen:** Für `day-packet-feed.xml` sollten `pubDate`-Werte so gewählt werden, dass sie auf der Ausführungsmaschine eindeutig auf die beabsichtigten **lokalen** Kalendertage fallen (z. B. Orts-Mittag statt Tagesgrenzen) — das Zeitzonen-Risiko im Plan nennt die Problematik nur für Unit-Test-Seeds.
- **`HasMore`-Randwert:** Endet ein Paket exakt auf einer vollen Seite (`items.Count == PageSize`), bleibt `HasMore` zunächst `true` und ein weiteres `LoadMore` liefert 0 → bestehendes Muster, kein Handlungsbedarf, aber beim Test `LoadMoreCommand_PagesWithinPacket_StopsAtEnd` mitbedenken.
- **`UnreadPacket`-Label-Komposition:** Bei erweiterten Paketen über zwei Tage bzw. undatiert+datiert ist die Formatierung von `{1}` („Ortsdatum(e)", `UnreadNoDateLabel`) im Detail offen — Implementierung sollte die Kombinationen eindeutig festlegen (z. B. „12.11. + 14.11.", „ohne Datum + 15.11.").
