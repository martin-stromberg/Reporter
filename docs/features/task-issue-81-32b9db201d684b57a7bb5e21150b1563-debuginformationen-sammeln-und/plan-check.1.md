# Plan-Gegenprüfung

## Ergebnis

**Status:** Plan lückenhaft

Der Plan deckt die Anforderung inhaltlich sehr vollständig ab: Alle fachlichen Muss-Anforderungen (Diagnose-Abschnitt auf der `SettingsPage`, persistierter Opt-in-Schalter `DebugCollectionEnabled`, Versand als vorbefüllte E-Mail über `Email.ComposeAsync`, Gateway-Muster, Report-Inhalte, `IsSupported`-Fehlerpfad, Lokalisierung, DI, Migrationen, manuelle Verifikation gemäß `AGENTS.md`) sind als ausführbare Schritte beschrieben und mit konkreten Tests hinterlegt. Die Stichproben-Verifikation im Code bestätigt die Planbehauptungen (u. a. `App.OnStart` mit `MigrateAsync()` und exakt vier Catch-Blöcken in `src/Reporter/App.xaml.cs`, alle 19 `new Settings`-Initializer im Repo vollständig in der Risikoliste erfasst, 29 `Debug.WriteLine`-Stellen, `PublicResXFileCodeGenerator` in `src/Reporter.Core/Reporter.Core.csproj`, `OrderByDescending(StartedAt)` in `SyncLogRepository.GetAllAsync`). Drei kleinere Lücken/Unstimmigkeiten bleiben (siehe unten).

## Fehlende oder unvollständige Planbestandteile

- [ ] Guard für die Senden-Aktion unterspezifiziert: `SendDebugReportAsync` ist nur mit `null`-/`IsSupported`-Guard beschrieben (`plan.md` Z. 137), der Test `SendDebugReport_CollectionDisabled_DoesNotSend` erwartet aber „Command löst keinen Versand aus". Zu klären/festzulegen: Guard auf `DebugSendEnabled`/`DebugCollectionEnabled` in `SendDebugReportAsync` oder `CanExecute` des `SendDebugReportCommand` — die reine UI-Deaktivierung per `IsEnabled`-Binding verhindert keinen programmatischen Aufruf.
- [ ] resx-Aufzählung unvollständig für den Report-Body: `plan.md` Z. 79 spricht von „Abschnitts-Headern (u. a. `AppResources.DebugReportSectionSessionLog`)", listet aber nur diesen einen Schlüssel. Entweder fehlen die Schlüssel für die übrigen sechs Sektionen oder es fehlt die explizite Entscheidung, dass Header als Literale formatiert werden.
- [ ] Kleinigkeit: Schritt 8 nennt als Voraussetzung „Schritte 4 und 8" (Selbstbezug) — gemeint ist offensichtlich Schritt 11 (DI-Registrierung); der nachfolgende Hinweis relativiert das, die Angabe ist dennoch fehlerhaft.

## Hinweise

- Die Planbehauptung „MAUI bietet kein verlässliches `IsComposeSupported`" ist ungenau: `IEmail.IsComposeSupported` existiert in `Microsoft.Maui.ApplicationModel.Communication`. Das gewählte Design (`IsSupported`-Property + Kapselung von `FeatureNotSupportedException` auf `false`) bleibt korrekt und testbar; bei der Implementierung kann `Email.Default.IsComposeSupported` für `IsSupported` herangezogen werden — keine Planlücke, nur Präzisierung für die Umsetzung.
- `IDebugLogService.SetEnabled(bool)` ist als `void` deklariert, soll aber einen `Lifecycle`-Übergangseintrag schreiben (DB-Zugriff) — das impliziert fire-and-forget `LogAsync` im Setter. Funktional konsistent, aber bei der Umsetzung bewusst zu gestalten (Fehlerpfad darf wie spezifiziert nie werfen).
- `SetEnabled(true→false)`-Übergang (Abschalten stoppt weitere Einträge) ist implizit über `LogAsync_Disabled_WritesNothing` und `DebugCollectionEnabled_Change_CallsSetEnabled` abgedeckt; ein expliziter Übergangstest wäre optional sinnvoll.
- Für das Seeding von `sync_logs`/`debug_log_entries` in den neuen Report-/E2E-Tests ist kein eigenes Helper geplant — die Repositories (`ISyncLogRepository.AddAsync`, `IDebugLogRepository.AddAsync`) können direkt genutzt werden; falls sich wiederholendes Setup ergibt, wäre eine `TestDataSeeder`-Erweiterung naheliegend.
- Der Upgrade-Pfad realer Bestandsdatenbanken (Migration statt `EnsureCreated`) ist wie im Bestand nicht automatisiert testbar; der Plan benennt das Risiko korrekt (`plan.md` Z. 213) und sichert das Schema über `EnsureCreatedAsync_CreatesQueryableTables` ab.
